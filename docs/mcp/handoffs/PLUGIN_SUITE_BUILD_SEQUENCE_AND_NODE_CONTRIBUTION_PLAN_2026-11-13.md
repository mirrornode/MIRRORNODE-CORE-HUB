**Purpose:** A reviewable sequence for building a bounded private demonstration of the THEIA / PTAH / THOTH constellation, MIRRORNODE Lattice, OSIRIS service journey, and @mirror provenance boundary.

## 2. Product architecture to preserve

| Surface | Candidate job in the suite | Boundary |
|---|---|---|
| THEIA | Help a person understand the case, see the relevant relationships, and reach the next authorized step | Coordinates and explains; does not override another node’s verdict or create approval |
| THOTH | Examine evidence, provenance, uncertainty, contradiction, and security exposure | Keeps its security lane distinct from Hermes routing and from THEIA synthesis |
| PTAH | Assess architecture, implementation feasibility, custody, and controlled change proposals | Key custody and execution authority must be mechanically enforced; product identity alone proves neither |
| MIRRORNODE Lattice | Carry consent-scoped references, identity/tenant context, handoffs, receipts, revocation, and continuity between surfaces | Private governed substrate first; not a raw ledger or shared secret store |
| @mirror | Remain the canonical source/provenance mechanism and preserve the narrow semantics of its validation receipts | A digest is not a truth claim or an approval token |
| OSIRIS | Deliver the client-facing audit-to-solution journey: scope, evidence, findings, remedy proposal, review, approval, verification, delivery, and receipt | A paid or connected workflow is not live until each operational stage is evidenced |

Distinct node presences remain distinct. A common plugin package, server, user interface, shared case schema, or lattice does not by itself prove independent identity, custody, authority, or permission boundaries. Those boundaries must be implemented and tested.

## 3. First proof: one synthetic case, one complete journey

The first useful demonstration should be a single synthetic small-business operations case with a fixed, disclosed scope and a small set of artificial evidence artifacts.

1. OSIRIS presents the synthetic engagement scope and known inputs.
2. THOTH labels each evidence item, source, age, limitation, contradiction, and confidence without promoting an inference to an observation.
3. PTAH returns an architecture/remediation proposal and names the preconditions for any future controlled change. It performs no mutation.
4. THEIA renders a concise client-facing explanation and a separate operator handoff, preserving open questions and node-specific conclusions.
5. @mirror records or validates only a synthetic receipt through a canonical, side-effect-free path. The receipt wording states exactly what the digest check establishes.
6. The Lattice stores only synthetic, allowlisted case references and handoff state in the pilot. No real customer, family, payment, credential, repository secret, or production record enters the demonstration.

A prototype must label synthetic outputs visibly. Until a later authorized connection is actually observed, the product must not claim live MCP access, client authentication, independent custody, cross-node connectivity, verified remediation, or production readiness.

## 4. Contribution cadence for every build gate

For each stage, THEIA prepares the same bounded packet for the participating nodes: exact document or commit reference, the question being decided, the proposed change, evidence classes, acceptance condition, and what is outside scope. Each participant returns its own view. THEIA integrates the responses and preserves disagreements; Siseon decides priorities, authorization, and covenants.

Every response should state: exact source/version reviewed; OBSERVED, REPORTED, INFERRED, PROPOSED, BLOCKED, UNKNOWN, and DECISION_NEEDED items; the participant’s conclusion and uncertainty; the smallest change or test needed; and whether the response is advisory or a formal role-bound disposition. A model response must not be labeled a formal PTAH or THOTH verdict unless its identity and review process satisfy the applicable governance requirements.

|---|---|
| A — Scope and baseline | Merlin maps dependencies and sequence. Hermes verifies source routing and current platform requirements. Gemini examines whether a first-time client can understand the service promise. Grok identifies the commercial hypothesis and what evidence would falsify it. Claude reviews technical feasibility in the proposed PTAH lane. THOTH identifies authority, disclosure, and security blockers independently. @mirror anchors canonical provenance semantics. THEIA reconciles the packet. Siseon sets the exact scope. |
| B — Contracts and interaction | Claude/PTAH proposes implementation boundaries, capability schemas, custody, failure behavior, and rollback. Merlin sequences dependencies without becoming a dispatcher. Gemini reviews the client workflow and accessibility. Grok pressure-tests packaging and offer language against evidence. @mirror checks canonical source ownership and receipt wording. THEIA records contradictions and presents decisions to Siseon. |
| C — Isolated synthetic build | The designated implementer creates a separate, synthetic-only branch or workspace after the execution owner and scope are explicitly selected. Claude/PTAH advises on architecture and implementation boundaries. Gemini reviews the functioning surface. Merlin tracks prerequisites and blocked dependencies. Hermes checks external requirements and source links. Grok checks whether the demo communicates a measurable buyer outcome. THOTH reviews the exact build artifact independently. @mirror supplies only the authorized provenance interface or a clearly labeled synthetic fixture. These are proposed assignments for this build, not new standing role grants. Gemini’s and Grok’s contribution lanes should be confirmed with their own responses. Claude’s advisory response does not automatically become a formal PTAH position. THOTH’s security lane remains separate from Hermes.
