# 0. How to read this dossier

MIRRORNODE has accumulated enough architecture, governance, runtime, audit, review, and product surface that a flat system summary is no longer safe.

This dossier therefore separates four evidence classes throughout:

- **OBSERVED** — directly established from a current repository, immutable head, workflow result, or other inspected evidence.
- **RECORDED** — present in MIRRORNODE documentation or governance records, but not independently re-observed in this dossier pass.
- **PROPOSED** — explicitly under review or construction; not yet canon or runtime authority.
- **UNKNOWN / NOT REVIEWED** — inventoried but not sufficiently inspected to support a stronger statement.

No lower evidence class is silently promoted because it is convenient.

The same rule applies to review claims:

`SCHEMA_VALID`
→ `SEMANTIC_VALID`
→ `TEST_SUITE_PASS`
→ `ADVERSARIAL_PROBES_PASS`
→ `EXACT_HEAD_REVIEWED`
→ `INDEPENDENT_EXACT_HEAD_REVIEWED`
→ `CONSTITUTIONALLY_CLEARED`
→ `MERGE_AUTHORIZED`

No lower claim implies a higher one.

# 1. Executive description

MIRRORNODE is a human-governed multi-agent systems architecture organized around explicit authority boundaries, evidence continuity, bounded execution, auditability, and differentiated operational roles.

Its central design problem is not simply orchestration. It is maintaining coherence between:

- intent;
- identity;
- authority;
- implementation;
- execution;
- evidence;
- review;
- interpretation;
- and final human disposition.

The current architecture increasingly separates these functions rather than asking one agent, model, repository, or interface to perform all of them.

The strongest recurring invariant is:

> **Evidence may support authority. Evidence is not authority merely because it exists.**

A passing test, a digest, a review, an AI statement, a green workflow, a repository permission, a mergeability flag, a Council position, or a user interface state must therefore remain attributable to its actual semantic level.

# 3. Authority topology

MIRRORNODE's current direction favors explicit role separation.

At minimum, an authority-bearing action may involve distinct identities for:

- requesting actor;
- maintaining actor;
- authorizing authority;
- executing actor/adapter;
- external provider;
- reviewer;
- independent confirmer;
- Operator.

These roles may sometimes be occupied by the same human or implementation system, but their semantic functions should remain separately attributable.

The core rule is that capability does not self-generate authority.

A model can reason about a change without being permitted to execute it.

A repository credential can allow an API mutation without constituting MIRRORNODE authorization for that mutation.

A successful verification can support a later authorization without becoming that authorization.

A UI may expose an available transition without becoming the source of the transition's legal basis.

# 5. Verification architecture — Thea and Oracle

## 5.1 Why Thea exists

The PR #53 review cycle exposed two distinct problems:

1. technical review incompleteness;
2. operational dependence on scarce external automated-review quota.

The response is an owned verification architecture rather than an attempt to copy one vendor model.

## 5.2 Thea deterministic layer

Current proposed v0.1 Thea checks include:

- strict manifest types;
- immutable Git identifier shape;
- normalized repository-relative path denotation;
- bounded operation vocabulary;
- write-target and destination collision analysis;
- positive artifact containment;
- artifact/implementation-scope separation;
- protected `.git` / `.github` artifact roots;
- verification-specific authorization presence;
- verification external-effect separation;
- supplied status-path-set agreement;
- working-directory/report-binding equality;
- limited handoff-lineage-reference checks;
- refusal-first adversarial probe scoring.

### Current claim limit

Thea v0.1 is currently a **supplied-manifest semantic verifier**.

It does not yet independently prove:

- that a repository checkout is actually at the supplied head SHA;
- that the supplied changed-file list equals the real Git diff;
- that a raw Git status capture agrees with the supplied parsed representation;
- that a handoff scope digest is authentic, recomputed, or complete.

A finding-free result therefore does not itself satisfy `EXACT_HEAD_REVIEWED`.

## 5.3 Oracle

Oracle consumes Thea evidence and uses a locally controlled model to generate adversarial hypotheses and synthesis.

The current proposal explicitly prevents Oracle from:

- erasing deterministic P1/P2 findings;
- converting HOLD to authority;
- claiming independence when provenance is contaminated;
- silently falling back to a cloud model.

The initial model adapter is loopback-only.

## 5.4 Review memory

Thea's review memory makes serious escaped defects permanent probe families.

This turns high-cost review failures into low-cost future regression checks.

The later evidence therefore withdrew the implication that 47/47 passing demonstrated adversarial completeness.

This distinction is foundational:

> **The test result remained true. The confidence inference was withdrawn.**

The decisive adversarial pass was performed by the correction-lane agent against its own correction. It was technically valuable but did not constitute independent review provenance.

The #53 branch was deliberately left unchanged while the learning was moved into Thea so the reviewed target remained immutable evidence.

# 8. Review doctrine

MIRRORNODE review should use orthogonal lenses rather than several reviewers repeating the same review posture.

The current eight-lens model is:

1. **Structural/schema** — what records/states are representable?
2. **Semantic invariant** — can internally valid fields contradict each other?
3. **Denotational/resource** — what do identifiers/paths actually resolve to?
4. **Authorization lifecycle** — who may do what, when, and until when?
5. **Adversarial state transition** — can valid records reach forbidden states?
6. **Provenance** — who implemented, corrected, reviewed, and synthesized?
7. **Human/machine divergence** — can a human see different evidence than enforcement consumes?
8. **Self-modification** — can the subject modify its validator, CI, policy, instructions, or evidence mechanism?

Denotational and self-modification lenses should be mandatory when a change affects authority or scope.

---

# 9. Correction-pass doctrine

One of the clearest lessons from #53 is that a bounded implementation correction must not imply bounded reasoning.

Recommended rule:

> **Implementation scope stays narrow. Verification scope widens around the changed invariant.**

Every correction should be attacked for:

- newly created authority surfaces;
- inverse privileges;
- negative constraints lacking positive containment;
- normalization/aliasing gaps;
- destination effects;
- evidence divergence;
- self-modification;
- provenance contamination.

If a correction discovers a new live P1 outside the currently authorized implementation scope, implementation stops and returns to Operator disposition.

# 12. NIST and market alignment

MIRRORNODE does not claim certification merely because its architecture maps well to external standards.

The current Thea/verification design is intended to produce evidence useful for a NIST-aligned program.

## 12.1 AI RMF

The architecture maps naturally to NIST AI RMF functions:

- **GOVERN:** roles, authority boundaries, review provenance, retained failure history;
- **MAP:** immutable target/scope and affected-authority mapping;
- **MEASURE:** deterministic checks, adversarial probes, severity and uncertainty;
- **MANAGE:** HOLD dispositions, bounded next actions, regression memory, iterative correction.

NIST AI RMF 1.0 remains the published framework while NIST is working on a revision.

## 12.2 Generative AI Profile

NIST AI 600-1 is relevant to model-specific risk such as uncertainty, misuse/abuse, provenance, human oversight, evaluation, and monitoring.

## 12.3 SSDF

NIST SP 800-218 SSDF v1.1 remains the final baseline.

NIST SP 800-218A is final and provides AI/dual-use foundation-model secure-development practices relevant to Oracle/model lifecycle and acquisition.

NIST SP 800-218 Rev. 1 / SSDF v1.2 is an Initial Public Draft dated 2025-12-17 and should be tracked as a forward reference rather than treated as the final controlling version.

## 12.4 Market expectations

Current AI code-review products make automatic re-review, repository-specific instructions, file-specific findings, agent instructions/skills, and broader tool context reasonable baseline expectations.

MIRRORNODE's intended differentiation is not merely another model reviewer. It is:

- owned availability;
- deterministic refusal below model reasoning;
- immutable-target claim discipline;
- provenance/independence tracking;
- permanent adversarial memory;
- explicit authority non-escalation;
- finding lineage;
- operator projection of known, unknown, and unauthorized states.
